## Initiative-sized, not yet scoped

- **STUB — a fixed-cost measurement infrastructure package.** Ian, 2026-09-09: package the learnings from 14 phases into a productized offering. **The selling point is the pattern of the whole thing, including the AI implementation** — not the stack (sGTM on Cloud Run, Consent Mode v2 and the container work are non-trivial, but they are not special), and not merely the evidence that it works, which is table stakes. What is differentiated is a repeatable way to build and keep a measurement stack correct, where an AI does the work and the verification discipline is what makes that safe.

  Raw material already exists and is worth inventorying before scoping: the two archived initiatives (`docs/initiatives/`), the runbooks, the manual-card convention, the review gates and their findings, the reconciler pattern, and guv itself.   Two problems to solve in scoping rather than assume away: the code does not transfer (the reconciler is shaped around this container; every client's GTM differs), so what transfers is the architecture plus the verification harness, rebuilt per client — which prices like services and packages like a product. And the differentiator is a practice, not a deliverable, so the value is ongoing rather than a handover.

  **A likely phase shape**, from the 2026-09-09 discussion: inventory what is actually packageable → the verification harness → **dependency currency** → client-facing artifacts → scope and pricing. Currency sits third because it depends on the harness existing and is the clearest ongoing-value story.

  **Dependency currency is a phase of this, not its own initiative.** Making it one would mean flipping the manifest back to `phased` for a single concern, weeks after deliberately flipping it to `task`. Ian's framing for it — build the process, then apply it to the backlog of Dependabot PRs — is the right shape, and those PRs are unusually good test material: a runtime major, an ESM-only break, a styling rewrite, a warehouse-compiler major, and one all-minor PR that fails anyway.   **Scope it tight when planning.** The honest minimum for currency is: CI runs the suites, majors are not grouped, and a written ladder says what to verify per risk class. Roughly a day. A phase gives that room to become a dependency-management framework nobody asked for.

## Cost

- **Nobody can attribute a dollar to a service** — there is no BigQuery billing export, so the only cost signal is the `metabase-project-budget` alert at $200/month (thresholds 50/90/100%, notifying `ops-email` since [13.1]). An alert tells you the total crossed a line; it cannot tell you which service moved. **Do this first** — every item below is an estimate from published rates until it exists, and a wrong guess here optimises the wrong service. **Half-done 2026-09-09**: `iampatterson:billing_export` created in `US`, and `docs/manual/task-2026-09-09-002.md` carries the remaining step. It is a browser step by necessity — `gcloud billing` has no export subcommand, verified against the installed SDK, and there is no public API for the toggle. Backfill is not retroactive, so the collection window starts whenever it is switched on. _(measured 2026-09-09)_
- **Two services pay for a full vCPU around the clock** — `sgtm` and `metabase` both run `min-instances=1` **and** `cpu-throttling: false`, which means CPU is allocated continuously rather than only during requests. That pairing is the single largest structural cost in the project, and it is the one worth testing before anything else. Both have a defensible reason to be warm — sGTM answers every visitor hit, and Metabase's JVM cold start would break the dashboard embedded on the ecommerce confirmation page — but *warm* is `min-instances=1`, which throttling does not undo. The question to test is narrower than it looks: does either need CPU **between** requests? For sGTM, probably not. For Metabase, possibly yes (scheduled syncs and cache warming run outside a request), so try sGTM first, measure, then decide. `event-stream` and `claudish-proxy` also hold `min=1` but are already throttled, which is the cheaper shape. _(measured 2026-09-09)_
- **The Metabase load balancer is a fixed monthly charge for one user** — one global forwarding rule plus the IAP path, serving a BI tool whose human audience is one person, and whose demo audience reaches it through an embed. It buys the custom domain and the IAP gate. Worth pricing against the alternative (IAP-less private access, or Cloud Run's own URL) before assuming it must stay. _(measured 2026-09-09)_
- **The GA4 BigQuery export runs daily and nothing reads it** — `analytics_530123649` holds 252 tables and 6.05 GB, from `events_20260326` to `pseudonymous_users_20260908`, growing every day. A repo-wide grep finds no query against it, and it duplicates what the sGTM to Pub/Sub to `events_raw` path already captures, which is the pipeline this site exists to demonstrate. Storage is pennies today; the point is the curve and the tidiness, not this month's bill. Decide: keep it as a comparison baseline (and say so), or turn the export off. _(measured 2026-09-09)_
- **Ruled out, so nobody re-investigates it** — BigQuery storage for this project's own data is not a cost factor: `iampatterson_raw` 0.28 GB, `staging` 0.27 GB, `marts` 0.20 GB, `assertions` ~0. Under a gigabyte all in, well inside the free tier. Query spend is not measured (see the first item), but at this data size it is unlikely to matter. The data generator's 194k sessions cost far more in Cloud Run invocations than in storage. _(measured 2026-09-09)_
- **The generator's cadence is a lever nobody has priced** — three Cloud Scheduler jobs, hourly 09:00–17:00 on weekdays, so 27 cold starts a day at 1 vCPU / 1 GiB. It exists to keep the dashboards populated. Now that `08_real_vs_generated_sessions` makes the real/generated split visible, the honest question is how much generated volume the demo actually needs: half the cadence would halve that line and still leave the charts populated. _(measured 2026-09-09)_

## Tooling and hygiene

- **CI's first real run found two things local runs cannot** — and one prediction of mine was wrong. `test.yml` DID run on the pull request: for a `pull_request` event GitHub takes workflows from the head ref, not the base. I stated the opposite in the PR body and here, which is `pull_request_target` behaviour. The two findings: `event-stream/src/server.test.ts` failed `TS18046` because `res.json()` is `unknown` on that service's own dependency set — it typed as `any` locally only because TypeScript walks up to the repo-root `node_modules/@types`, which a per-service `npm ci` does not have, and neither does the Dockerfile build. And `claudish-proxy`'s jest workers were killed: `adapters.ts` imports both Anthropic SDKs at top level, ts-jest compiles that surface per worker, and jest sizes its pool from the host CPU count — 14 locally, far fewer on a runner. Both fixed. **This is the class of defect the workflow exists for.** It is reproducible locally once you know how — restrict type resolution to the service's own types, which is what a per-service `npm ci` gives:

  ```bash
  cd infrastructure/cloud-run/<service>
  npx tsc --noEmit --typeRoots ./node_modules/@types --lib ES2022 \
    --module commonjs --esModuleInterop --strict --skipLibCheck src/*.test.ts
  ```

  Run that before pushing a service change rather than using CI as the compiler. I fixed the first reported line, pushed, and CI reported the next one in the same file — the compiler stops at the first error, so fixing the instance rather than the class costs a full round trip each time. _(2026-09-09, run 34407465187)_
