# Claudish MCP server: scope

Status: scoping only. Nothing implemented. Written 2026-09-01 against branch
`feat/claudish`.

Goal: let Ian run Claudish translations from inside a Claude chat (Claude Code,
Claude Desktop, claude.ai) instead of tabbing to `/claudish`.

Everything below about the MCP ecosystem was checked against primary sources
today. Where a source did not answer the question, this document says so.

## 1. What the MCP server actually adds, and where it adds little

Inside a Claude chat, the model can already imitate Claudish. It is Claude. Ask
it to write like an LLM and it will do a passable job. So be clear about what
the tool buys:

- **It does not add much for en2cl.** The engine is Claude Haiku 4.5 behind a
  tuned system prompt and few-shot set (`src/prompts/`, `PROMPT_VERSION` v8).
  Better than an ad-hoc instruction, reproducible, cached, but a chat Claude
  asked nicely lands nearby. The tool gives the canonical translation, not the
  only possible one.
- **It adds a lot for `detect`.** CCLD is a real trained model (27,026
  parameters, 92.9% accuracy on the project-held-out split, per
  `docs/claudish/ccld-model-card.md`). A chat Claude asked "is this Claudish?"
  is guessing. This is the tool that cannot be faked in-context.
- **It adds a lot for cl2en.** That direction is not a prompt, it is a
  judge-driven refinement loop on Gemini 2.5 Flash with up to five attempts
  scored by the detector ensemble (`src/cl2en-loop.ts`, `src/judge.ts`). A chat
  Claude does one pass with no adversarial scoring.
- **It adds the share link**, the `/claudish?t=` URL Ian actually sends people.

So: build it for `detect`, `cl2en`, and `share_link`. `translate` in the en2cl
direction is table stakes, not the reason.

## 2. The three surfaces

### Claude Code

`claude mcp add --transport http|sse|stdio`, with `--header` for static auth,
`--scope local|project|user`, and `.mcp.json` for project scope. OAuth works via
`/mcp` or `claude mcp login`, and pre-registered credentials via `--client-id` /
`--client-secret`. Source: <https://code.claude.com/docs/en/mcp>.

The cheapest surface to serve. A bearer header is enough:

```
claude mcp add --transport http claudish https://claudish-proxy.../mcp \
  --header "Authorization: Bearer $CLAUDISH_MCP_TOKEN"
```

Timeouts from the same page: a per-request timer of `max(60s, per-server
timeout, MCP_TIMEOUT)`, a 5 minute idle window for HTTP, and auto-backgrounding
past 2 minutes. A per-server `timeout` in `.mcp.json` is a hard wall clock and
progress notifications do not extend it. The 40s worst-case loop fits inside the
60s floor untouched. Tool output is capped at 25,000 tokens
(`MAX_MCP_OUTPUT_TOKENS`), far above a 3,000-character translation.

### Claude Desktop

Two separate paths. Remote connectors use the same infrastructure as claude.ai
(next section). Local stdio servers are configured in
`~/Library/Application Support/Claude/claude_desktop_config.json` on macOS
(`%APPDATA%\Claude\...` on Windows), reachable via Settings > Developer > Edit
Config, with the familiar `{"mcpServers": {"name": {"command": ..., "args": [...],
"env": {...}}}}` shape and a full restart to reload.
Source: <https://modelcontextprotocol.io/docs/develop/connect-local-servers>.
Anthropic notes local servers "aren't available in Cowork or claude.ai".

### claude.ai custom connectors

Adding one is Customize > Connectors > "+" > Add custom connector, with the
server URL required and OAuth client id/secret optional under Advanced settings.
Free, Pro, Max, Team and Enterprise; Free is limited to one; on Team and
Enterprise only Owners can add them.

**The important correction to the obvious assumption: OAuth is not required.**
Anthropic documents six auth types for remote MCP servers, and two of them make
this project easy:

| Type | What it is | Availability |
| --- | --- | --- |
| `oauth_dcr` | OAuth with Dynamic Client Registration | Out of the box |
| `oauth_cimd` | OAuth with Client ID Metadata Document | Out of the box |
| `oauth_anthropic_creds` | Anthropic holds your client credentials | Contact Anthropic |
| `custom_connection` | Credentials supplied at connect time | Contact Anthropic |
| `static_headers` | Fixed API key or bearer token as a request header | **Beta** |
| `none` | **No authentication (authless server)** | **Supported** |

Source: <https://claude.com/docs/connectors/building/authentication>. Verbatim on
`none`: "No authentication (authless server) ... Supported. An optional
partial-auth mode is experimental."

Caveats before leaning on `static_headers`: it is beta, the credential is
"entered by an organization administrator ... shared by the organization rather
than pasted per user", and `authorization` / `x-api-key` are pre-approved header
names while others need Anthropic's review. Whether an individual Pro account
gets it at all was not confirmed. Credentials in the URL query string are
explicitly discouraged.

Documented limits (<https://claude.com/docs/connectors/building>):

| Constraint | Limit |
| --- | --- |
| claude.ai / Desktop tool-call timeout | **300 seconds** |
| claude.ai / Desktop max tool result | ~150,000 characters |
| Anthropic egress range | `160.79.104.0/21` |

Tools, prompts and resources are all supported. Resource subscriptions and
sampling are not.

### Protocol facts that shape all three

The current spec revision is **2026-07-28**
(<https://modelcontextprotocol.io/specification/latest>):

- Streamable HTTP is a single POST endpoint. The GET stream and protocol-level
  sessions (`Mcp-Session-Id`) were **removed**, as was the `initialize`
  handshake. Requests carry `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name`
  headers that must match the body, or the server returns 400 with `-32020`.
- Servers **MUST** validate `Origin` and return 403 when it is present and
  invalid. The semantics differ from the proxy's existing gate (which rejects a
  missing origin too), so `/mcp` needs its own check.
- Cancellation is the client closing the SSE response stream, which maps onto
  the proxy's existing `res.on('close')` abort path.
- Authorization is **OPTIONAL**. If OAuth is implemented, the server MUST provide
  RFC 9728 protected resource metadata, and DCR (RFC 7591) is now **deprecated**
  in favor of Client ID Metadata Documents.
- A **Tasks extension** exists for long-running calls. Opt-in on both sides.

**Spec-current and works-with-Claude-today are different questions.** Anthropic's
connector page lists auth-spec support for 2025-03-26, 2025-06-18 and 2025-11-25
only. `2026-07-28` is absent. Claude Code's v2 runtime does negotiate the new
revision with HTTP servers, but a connector aimed at claude.ai should still serve
the older session-based era. The SDK's legacy-client mode handles both, which is
an argument for using it rather than hand-rolling the transport.

## 3. Tool surface

Four tools. All read-only in the sense that nothing is stored server-side.

**`claudish_translate`**

```
input:  { text: string (1..3000), direction: "en2cl" | "cl2en" }
output: structuredContent {
          text: string,
          direction, lane, cached: boolean,
          revised: boolean,          // cl2en only
          attempts: number,          // cl2en only
          judge_p: number | null,    // final detector score of the served text
          ttft_ms, total_ms
        }
        content: [ { type: "text", text: <the translation> } ]
```

The SSE frames collapse cleanly because MCP tool results are single values:

- `token` frames accumulate into `text`. Nothing is emitted per token.
- `revise` is *invisible* at this layer. Server-side the loop already discards
  losing attempts and only replaces on a meaningful gain, so the MCP result is
  simply the final `servedText`. This matches the frontend's concealed-draft
  behavior (`target-panel.tsx`, `concealDrafts = direction === 'cl2en'`) rather
  than fighting it. Report `revised: true` in structured output so the fact is
  available without being dramatic.
- `refusal`, `capacity` and `error` become tool execution errors: `isError: true`
  with the verbatim line from `src/lib/claudish/messages.ts`
  (`REFUSAL_MESSAGE`, `CAPACITY_MESSAGE`). Per the spec, execution errors go in
  the result with `isError`, not as JSON-RPC errors, so the model can react. A
  400/413 from bad input is also `isError: true` with the cap stated.
- Reserve JSON-RPC protocol errors for unknown tool and malformed request only.

**`claudish_detect`**

```
input:  { text: string (1..3000) }
output: structuredContent {
          lang: "en" | "en-x-claudish" | "unknown",
          confidence: number,        // P(claudish), 0..1
          source: "ccld" | "heuristic",
          label: string              // the UI tier string
        }
```

Zero model cost, zero network, about 1.6ms at the cap. Runs entirely on the
vendored detector already in the proxy (`src/vendor/`, `src/judge-loader.ts`).
This tool should be free of rate limiting beyond a coarse flood guard.

**`claudish_share_link`**

```
input:  { source, target, direction }
output: structuredContent { url, truncated: boolean, url_chars: number }
```

Pure function over `share-codec.ts`. No storage, no spend. Needs a vendored copy
of the codec plus `lz-string` (already a root dependency) in the proxy.

**`claudish_about`** (optional, cheap)

Returns the fixed facts: input cap, directions, what the detector is, the
"nothing is stored" claim, and the `/claudish` URL. Better as an **MCP resource**
than a tool, since it is reference material rather than an action. Consider
also exposing the model card as a resource. Prompts are not worth it here; the
tools are self-describing.

Notes: tool names SHOULD be 1 to 128 characters from `[A-Za-z0-9_.-]`, so the
`claudish_` prefix is fine and helps when several servers are connected. Set
`annotations: { readOnlyHint: true, destructiveHint: false, openWorldHint: true }`
on all four; `destructiveHint` and `openWorldHint` both default to `true`, so
saying nothing is the pessimistic reading. Those field names come from the spec
repo's `schema.ts`, not the rendered docs page, so confirm against the schema at
implementation time. Output size is not a concern on either surface: the caps are
25,000 tokens (Claude Code) and about 150,000 characters (claude.ai), against a
3,000-character input.

## 4. Architecture options

**(a) Thin MCP server, separate process, calls `/translate` over HTTP.**
Two deploys, two cold starts, SSE frames parsed twice, and the origin gate has to
start accepting a service identity: either Cloud Run IAM (`run.invoker` on the
caller's SA, an ID token audienced to the proxy URL, per
<https://docs.cloud.google.com/run/docs/authenticating/service-to-service>) or a
shared secret. Real work for no gain, since the two would sit side by side.

**(b) Second transport inside the existing `claudish-proxy` process.**
Add `POST /mcp` to `createApp()` next to `POST /translate`. Tool handlers call
`runCl2enLoop` and the lane ladder **directly**, not over HTTP. No second
serialization, no second auth boundary, no second budget tracker, one kill
switch. The rate limiter, `BudgetTracker`, `TranslationCache` and log allowlist
are already shared instances.

**(c) Local stdio server that talks to the proxy.**
Only helps Claude Code and Claude Desktop, never claude.ai, and still needs the
proxy to accept a non-browser caller. Inherits (a)'s auth problem while serving
fewer surfaces. A throwaway spike at best.

**Recommendation: (b).** One service, one budget, one kill switch, one privacy
boundary. The main cost is that `translate.ts` currently interleaves orchestration
with SSE framing, so the shared core needs to be extracted first.

Concretely: pull the direction-dispatch logic out of `createTranslateHandler`
into a `runTranslation(deps, {text, direction}, sink)` function where `sink` is
an interface with `token`, `revise`, and a terminal callback. `SseStream`
becomes one implementation of that sink; a buffering `CollectSink` for MCP
becomes the other. That refactor is worth doing on its own merits.

## 5. Auth and abuse

The proxy today is `--allow-unauthenticated` with an origin allowlist, per-IP
limits (20/min, 200/hr, 1000/day per instance), a $23/day model-spend cap and a
kill switch. The origin gate is the thing MCP breaks: Anthropic's servers will
not send an allowlisted `Origin`, and per the MCP spec they may send none at all.

Do **not** relax `requireOrigin` on `/translate`. Give `/mcp` its own gate. Three
controls, cheap and stackable, and none of them is OAuth:

1. **A static bearer secret.** A random 32-byte token in Secret Manager, checked
   constant-time. Claude Code passes it with `--header`. On claude.ai the
   `static_headers` beta may accept the same token, with `authorization` being a
   pre-approved header name, but that path is beta and appears aimed at org
   admins, so treat it as unproven until tried.
2. **An IP allowlist on `160.79.104.0/21`.** Anthropic publishes its egress range
   and all hosted-surface connector traffic comes from it. For a claude.ai
   connector this is the strongest single control available: it does not need a
   credential the connector form may not accept, and it reduces the open-relay
   risk to "someone inside Anthropic's range". Claude Code connects from Ian's
   own machine, so it needs the bearer path instead. Check the published range
   at deploy rather than hardcoding it forever
   (<https://platform.claude.com/docs/en/api/ip-addresses>).
3. **An unguessable path segment** (`/mcp/<random>`) as the connector URL. Not
   security, but it removes drive-by discovery, and the URL is pasted once.

Accept bearer **or** allowlisted source IP, and `/mcp` is defensible on every
surface without an authorization server. **OAuth is not needed and should not be
built.** DCR is deprecated spec-side, CIMD plus an AS is days of work and a
permanent liability, and `none` is documented as supported anyway.

The residual exposure is the same one `/translate` already carries, and the
README already says so: per-IP limits shape the happy path, the budget tracker is
the real backstop.

Whatever is chosen, `/mcp` must keep its own rate-limit bucket. A single Claude
session can fire several tool calls per turn, so 20/min per key is tight; 30/min
with the same hourly and daily ceilings is a reasonable starting point.

**Kill switch:** `KILL_SWITCH=on` makes `budget.reserve()` return null. On
`/translate` that is a 503 or a `capacity` frame. On `/mcp` it must become
`isError: true` carrying `CAPACITY_MESSAGE` verbatim, so the model reads a
sentence instead of a stack trace and does not retry in a loop. Say so in the
tool description: this tool can decline, and declining is not a bug.
`claudish_detect` and `claudish_share_link` keep working under the kill switch,
because neither spends anything.

## 6. Hosting and cost

Ride the existing service. Adding a route to `claudish-proxy` costs no new
Cloud Run floor. A second service at `min-instances=1` would roughly double the
always-on cost, which is the largest fixed line in this stack.

Per-call cost is unchanged: about $0.0025 for en2cl, about $0.0008 for cl2en,
up to about $0.016 on a cap-length input. One person in a chat is noise against
a $23/day cap. `detect` and `share_link` are free.

**Timeouts.** The service is deployed with `--timeout=60` (`setup.sh` line 113),
against a Cloud Run default of 300s and a maximum of 3600s
(<https://docs.cloud.google.com/run/docs/configuring/request-timeout>). The
cl2en loop's longest budget is 40s (`loopBudgetFor`, inputs over 2,000 chars),
leaving about 20s for network. Thin but workable. Raising the deploy to
`--timeout=120` before shipping `/mcp` is cheap insurance and changes nothing
about the loop.

On the client side there is no problem: Claude Code's per-request floor is 60s,
and claude.ai and Desktop allow 300s per tool call. **Do not implement the Tasks
extension.** It exists for minutes-long work, both sides must opt in, and client
support varies. A 40s blocking call is inside every documented budget with room
to spare.

Streaming is not useful here either. MCP can send `notifications/progress` on the
response stream, but a tool result is a single value and the chat shows nothing
until it lands. Return the finished translation.

## 7. Privacy and logging

The existing rule holds: input and output text never reach logs or analytics.
`src/log.ts` enforces it with a field allowlist and a test that greps captured
stdout for forbidden strings. Extending to `/mcp` means:

- Reuse `logEvent` unchanged. Add at most two allowlist fields, both non-text:
  `mcpTool` (the tool name) and `mcpClient` (`clientInfo.name` from `_meta`,
  which is "claude-code" or similar, not a user identity).
- **Do not annotate any Claudish parameter with `x-mcp-header`.** That feature
  mirrors argument values into HTTP headers, where intermediaries can see them.
  The spec warns against it for sensitive values, and translation input is the
  sensitive value here. By extension, do not log `Mcp-Name` blindly.
- MCP adds no user identifier unless OAuth is added, which is one more argument
  for not adding it.
- Whatever the rate-limit key becomes, keep hashing it through the existing
  per-instance salted `hashIp`.

## 8. Testing and rollout

**Local testing** uses MCP Inspector, `@modelcontextprotocol/inspector`, which
ships three clients behind one binary: web (default), `--cli`, and `--tui`. It
needs Node 22.19.0 or newer. For a remote HTTP server:

```
npx @modelcontextprotocol/inspector --server-url http://localhost:8080/mcp --transport http
npx @modelcontextprotocol/inspector --cli http://localhost:8080/mcp --transport http \
  --method tools/call --tool-name claudish_detect --tool-arg text="..." --format json
```

Inspector is at 2.4.0 and defaults to the **legacy** protocol era, so exercise
both via its `protocolEra` setting. CLI mode is scriptable, so it can run as a
shell check. One trap: the target URL must come before `--method` or it is
silently dropped.
Source: <https://modelcontextprotocol.io/docs/tools/inspector>.

**Unit tests** follow the existing pattern: `createApp(deps)` with `FakeLane`
injected, hit a real listening socket, assert on the JSON-RPC result. Zero
network, zero spend. Pins worth writing red first: `tools/list` returns exactly
four tools in stable order; a refusal produces `isError: true` carrying
`REFUSAL_MESSAGE` character for character; kill switch on produces
`CAPACITY_MESSAGE` while `claudish_detect` still succeeds; over-cap input
produces `isError: true` naming 3,000 rather than leaking a 413 as a protocol
error; `claudish_detect` agrees with `detectClaudish()` on the frontend's own
fixtures so the two cannot drift; and a log sweep over a full `tools/call`
contains neither input nor output text.

**Golden-style test:** extend `golden/` rather than duplicating it. A
`GOLDEN_TEST=1` case drives the MCP handler with the existing fixtures and
applies the same property assertions from `src/assertions.ts` (no em dashes in
cl2en output, no kill-list words, no preamble, canary token absent). The point
is that both paths produce output of the same quality, not identical strings.

**Rollout:**

1. Extract `runTranslation` with a sink interface. Ship it with the SSE path
   unchanged and all existing tests green. No new behavior.
2. Add `/mcp` with bearer auth and the four tools. Test with Inspector in both
   protocol eras, then `claude mcp add --scope user`. Use it personally for a
   week.
3. Add the `160.79.104.0/21` allowlist as a second accepted credential, then add
   the connector on claude.ai as an authless server and confirm it connects. This
   is now a one-afternoon step rather than an OAuth project.

## 9. Effort estimate

For option (b), roughly **4 to 6 developer-days** at this codebase's test
discipline, covering **both** surfaces: 1.0 day to extract `runTranslation` plus
the sink from `translate.ts` with SSE tests green; 1.5 days for the `/mcp`
handler, four tools, bearer plus IP gate, MCP origin check, rate-limit key and
kill-switch mapping; 1.0 day of tests; 0.5 day to vendor the share codec and add
the model-card resource; 0.5 day for Inspector runs, deploy and README; 1.0 day
of slack for the two protocol eras and SDK v2 novelty. The claude.ai connector
adds hours, not days, now that OAuth is off the table.

Files to add or change, all under `infrastructure/cloud-run/claudish-proxy/`:

- `src/run-translation.ts` and `.test.ts` (new; extracted core plus `CollectSink`)
- `src/translate.ts` (change; becomes the SSE sink over the extracted core)
- `src/mcp/server.ts` (new; `McpServer` instance, `registerTool` x4, resources)
- `src/mcp/tools.ts` and `.test.ts` (new; schemas and handlers)
- `src/mcp/auth.ts` and `.test.ts` (new; bearer check, CIDR check, origin check)
- `src/vendor/share-codec.ts` (new; copy of the frontend codec, behavior-pinned
  against it like `judge-loader.ts` is)
- `src/server.ts` (change; mount the MCP route)
- `src/config.ts` (change; `MCP_ENABLED`, `MCP_BEARER_SECRET`, `MCP_ALLOWED_CIDRS`,
  MCP rate limits)
- `src/log.ts` (change; two new allowlist fields)
- `package.json` (change; `@modelcontextprotocol/server`,
  `@modelcontextprotocol/express`, `lz-string`)
- `setup.sh` (change; `--timeout=120`, new env vars from Secret Manager)
- `README.md` (change; MCP section, updated kill-switch runbook)

Note on packages: the SDK's v2 line publishes as `@modelcontextprotocol/server`,
`/client`, `/express` and `/node` (2.0.0) and implements 2026-07-28. The older
`@modelcontextprotocol/sdk` (1.30.0) is the v1 line and stays supported for at
least six months. Prefer v2: it is stateless by default and its legacy-client
mode serves the 2025-era clients claude.ai still needs. The v2 API is
`createMcpHandler(() => server)` plus `createMcpExpressApp()` and
`toNodeHandler()`, not v1's `StreamableHTTPServerTransport`; tools register with
`registerTool` and take a full `z.object({...})` rather than a raw zod shape.
Register tools inside the factory, never on a shared instance. Confirm the API
against <https://ts.sdk.modelcontextprotocol.io/v2/serving/express> at
implementation time, not against blog examples.

## 10. Open questions for Ian

1. **Is an IP allowlist an acceptable primary control for claude.ai?** It is the
   pivot of section 5. It means trusting that anything inside
   `160.79.104.0/21` is legitimately Ian's session, which is true in the sense
   that matters (only a Claude client reaches it) but false in the strict sense
   (any Anthropic user's connector could point at the URL). Paired with the
   budget cap and the unguessable path, this reads proportionate for a toy. Ian
   should confirm he agrees.
2. **Should `claudish_translate` exist at all, or ship `detect` plus `share_link`
   first?** The detector is the part a chat Claude genuinely cannot do. A
   detect-only v1 costs about 2 days, spends nothing, needs no budget wiring,
   and is unarguably useful.
3. **Raise the Cloud Run timeout to 120s?** Recommended, low risk, but it is a
   deploy-shape change on a service that is currently tuned.
4. **Does the MCP path get its own `PROMPT_VERSION` visibility?** Returning it
   in structured output is free and makes results traceable, but it also puts an
   internal version string in front of anyone who connects.
5. **Public or private?** This document assumes the server is for Ian. If the
   connector URL is ever published as part of the portfolio story, the abuse
   analysis in section 5 changes and the budget cap becomes the only wall.
6. **Is the connector worth submitting to Anthropic's directory?** Out of scope
   here, and it would raise the traffic profile substantially, but it is the
   obvious portfolio move if the thing works and Ian wants the reach.

The question this document originally expected to ask, "OAuth or accept being
open", is closed. Anthropic documents authless connectors as supported, so
neither horn of that dilemma applies.
