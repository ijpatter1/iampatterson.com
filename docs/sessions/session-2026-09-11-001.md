## What this session was

An API key named "assistonauts" in Ian's Anthropic org billed $99.15 of Fable 5.1 between 22:00 and 22:26 UTC on 10 September and triggered a $93.87 auto-recharge. The investigation started on the Mac and found nothing, because the caller was not local. The key had been stored as a setting in this project's self-hosted Metabase, which served every API path to the internet.

**CVE-2026-72898** is an unauthenticated SQL injection in `/api/session/reset_password`, published 2026-08-06 and first patched in 0.59.21. This instance ran v0.59.6 behind a load balancer that carved all of `/api/*` out from IAP. Cloud Run request logs show it exploited on 09-03, 09-04 and 09-10 from five addresses in AS48090 (DMZHOST / TECHOFF SRV LIMITED): each round is `POST /api/session/reset_password` returning 400, followed by an authenticated request as Metabase user 1. At **20:37:07–08 on 09-10**, one round then `GET /api/setting` (27,588 bytes), `/api/database` and `/api/api-key`. The settings response held the key. The billing burst began 83 minutes later.

Attribution is evidence, not inference; what remains unknown is who ran the client, which only Anthropic's request records can answer.

**The attacker audit came back clean, from evidence.** Across 30 days of request logs (2026-08-12 onward, the full exploitation window), the attacker addresses sent nothing but the exploit POST — no user, API key, card, subscription or setting written. Every successful write came from Ian's own address. No dashboard subscription ever fired, only scheduler initialisation. Limit worth stating: the flaw is SQL injection, so a write made directly against the database would not appear in HTTP logs; Ian confirmed People shows one account.

**Rotation proof:** a token signed with the old key returned 200 before the apply and **400 "Message seems corrupt or manipulated"** after — signature rejection, not expiry — and a freshly minted token returns 200 with real dashboard content. Secret Manager version 1 is disabled.

## The outage, and what caused it

Rotating the secret broke embeds for about **eleven minutes**. Revision `metabase-00006-zzk` failed its startup probe with `FATAL: remaining connection slots are reserved for non-replication superuser connections`, and the Vercel build signing with the new key had already been promoted.

Two distinct mistakes:

1. **Capacity was never checked.** `db-f1-micro` leaves ~22 connections usable after Postgres reserves its superuser slots, `MB_APPLICATION_DB_MAX_CONNECTION_POOL_SIZE` defaults to 15, and a Cloud Run rollout runs two revisions at once. Monitoring confirms it: `num_backends` idles near 11 and peaked at exactly 22 during the failure. This blocked *any* config change to the service, including the next security patch — so #85 is worth having regardless of the rotation.
2. **The halves were moved in the wrong order.** Promoting the site before Metabase was confirmed serving the new key turned a failed deploy into a visible outage. `docs/runbook/revision-will-not-start.md` now says a failed revision *is* an outage when it is one half of a two-sided change, with this as the worked example, and `infrastructure/metabase/README.md` carries the rotation sequence in the safe order. The retry produced no visible gap.
