# Manual Task — Vercel automation bypass secret

**Created:** 2026-09-05, session-2026-09-04-002
**Phase:** 13, deliverable 13.5
**Status:** pending
**Priority:** low — nothing is broken; this unblocks automated checks against preview deployments
**Blocks:** end-to-end and Lighthouse runs against Vercel previews. Everything else proceeds without it.

## Context

Deployment protection is on for preview deployments, which is the right default
for a consulting site: previews should not be publicly readable before they ship.
The side effect is that anything automated — Playwright, a Lighthouse capture, a
smoke script — receives Vercel's authentication page instead of the site, and its
failures look like application bugs.

Vercel's automation bypass secret is the sanctioned way through. A client that
sends the token reads the preview; a client that does not still meets the wall,
so the protection keeps working for people.

This cannot be scripted. Creating the secret is a browser action in the Vercel
dashboard, which is why it is a card rather than a step in a deploy script.

## Steps

1. Open the Vercel dashboard for this project, then **Settings → Deployment
   Protection**.
2. Find **Protection Bypass for Automation** and generate a secret.
3. Copy the value. Vercel shows it once.
4. Store it where the automated checks will read it. It is a secret, so it does
   not go in the repository: an environment variable named
   `VERCEL_AUTOMATION_BYPASS_SECRET` locally, and a GitHub Actions secret of the
   same name if a workflow ever needs it.
5. Verify against any current preview deployment:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' \
     -H "x-vercel-protection-bypass: $VERCEL_AUTOMATION_BYPASS_SECRET" \
     https://<preview-deployment>.vercel.app/
   ```

   Expect `200`. Then run the same request **without** the header and confirm you
   still get the authentication wall — that half proves the protection is intact
   rather than disabled.
