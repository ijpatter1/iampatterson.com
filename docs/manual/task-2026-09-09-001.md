## Why the order matters more than the steps

`vars.GCP_WIF_PROVIDER` is one variable with **two** consequences. Setting it
arms `infra-reconcile.yml`'s GTM apply *and* `infra-terraform.yml`'s
`terraform apply -auto-approve`, which has been sitting inert since Phase 11
behind exactly this gate. The second one applies to the Terraform root whose
plan, four months ago, proposed to destroy the event pipeline.

And GitHub creates a referenced-but-missing environment **implicitly, with no
protection rules**. So setting the variable before the environment exists does
not fail loudly — it silently produces an unreviewed auto-apply on every push to
`main`. Measured 2026-09-08: no `infra-production` environment existed, and the
two that did (`Preview`, `Production`) carried `"protection_rules": []`, while
`infra-terraform.yml` had asserted in a comment that repo settings required
manual approval.

`infra-reconcile.yml` now refuses to apply if the environment has no protection
rules, so the worst case is caught. The ordering below is what stops it arising.

## Steps

### 1. Create the environment, with a reviewer

Repository → **Settings → Environments → New environment** → name it exactly
`infra-production`.

Under **Deployment protection rules**, tick **Required reviewers** and add
yourself. Save.

Verify — this is the check the workflow itself runs:

```bash
gh api repos/ijpatter1/iampatterson.com/environments/infra-production \
  --jq '.protection_rules | length'
```

It must print a number greater than 0. If it prints `0`, the environment exists
but is unprotected and you are in the state this card exists to prevent.

### 2. Create the WIF pool, provider and deployer account

These do not exist yet. `infra-terraform.yml` has named them a prerequisite
since Phase 11 and the README follow-up that was meant to declare them was never
written.

```bash
gcloud iam workload-identity-pools create github \
  --project=iampatterson --location=global --display-name="GitHub Actions"

gcloud iam workload-identity-pools providers create-oidc github \
  --project=iampatterson --location=global --workload-identity-pool=github \
  --display-name="GitHub" \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository" \
  --attribute-condition="assertion.repository == 'ijpatter1/iampatterson.com'"
```

**The attribute condition is not optional.** Without it any GitHub repository in
the world can mint tokens for this pool.

```bash
gcloud iam service-accounts create infra-deployer \
  --project=iampatterson --display-name="Terraform + GTM deployer (CI)"

PROJECT_NUMBER=262727068689
gcloud iam service-accounts add-iam-policy-binding \
  infra-deployer@iampatterson.iam.gserviceaccount.com --project=iampatterson \
  --role=roles/iam.workloadIdentityUser \
  --member="principalSet://iam.googleapis.com/projects/${PROJECT_NUMBER}/locations/global/workloadIdentityPools/github/attribute.repository/ijpatter1/iampatterson.com"
```

### 3. Grant the deployer its roles, and write down why

To apply this Terraform root the deployer needs authority over compute, run,
sql, pubsub, bigquery, secretmanager and IAM — an identity close to the
`roles/editor` that [13.4] spent a deliverable removing from a runtime, now
reachable from any push to `main`.

[14.3] asks for the roles to be **recorded and justified**, not minimised:
deriving true least privilege for a whole-root deployer is a research task that
would eat the deliverable, and the boundary plus the approval gate is what the
phase must deliver. Record what you grant and why in
`docs/verification/`, and treat narrowing it as a follow-up.

### 4. Add the deployer to the GTM account

**The Tag Manager API authorises on GTM account membership, not GCP IAM.** WIF
gets the workflow an identity; it does not get it access. Without this the first
CI reconcile fails.

<https://tagmanager.google.com> → **Admin → Account User Management** on account
`6346433751` → add `infra-deployer@iampatterson.iam.gserviceaccount.com` with
**Publish** on both containers. Same procedure as
`docs/manual/task-2026-09-08-001.md`, which did this for the interactive
identity.

### 5. Only now, set the variables

```bash
gh variable set GCP_WIF_PROVIDER \
  --body "projects/262727068689/locations/global/workloadIdentityPools/github/providers/github" \
  --repo ijpatter1/iampatterson.com

gh variable set GCP_DEPLOYER_SA \
  --body "infra-deployer@iampatterson.iam.gserviceaccount.com" \
  --repo ijpatter1/iampatterson.com
```

**Before you run these**, confirm `terraform plan` is a no-op. There are five
imports declared and unapplied as of 2026-09-09 ([14.5]); if the variable is set
while those are outstanding, merging them means an unattended apply performing
the import of a live production service.

```bash
GOOGLE_OAUTH_ACCESS_TOKEN=$(gcloud auth print-access-token) \
  terraform -chdir=infrastructure/terraform plan
```

## How you know it worked

Open a pull request touching `infrastructure/gtm/**` — adding a comment to
`web-container.json` is enough. Within a minute or two the PR carries a comment
headed **"GTM reconciler — dry run"** with the diff for both containers. It
should read `no drift` on both, because the containers are converged.

Merge it. The `apply (main)` job should appear as **pending approval**, not
running. Approve it and watch the preflight step print
`infra-production carries N protection rule(s)` before anything applies.

If the apply starts without asking for approval, stop and unset
`GCP_WIF_PROVIDER` — the environment is not protected and step 1 did not take.
